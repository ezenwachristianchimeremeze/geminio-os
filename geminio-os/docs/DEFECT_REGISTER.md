# Defect Register (verification pass 2026-10-10/11, baseline v12)

Every entry was found by reading the code that has never run, fixed in this checkpoint, and covered by a regression test in `tests/verification-defects.test.ts` (VER-DEF-nnn). Evidence for all fixes is **static + offline shim tests (+ SQLite for DEF-008/009)**; none was reproduced on MySQL or through a live API, and no fix is "VERIFIED".

## Open findings (not fixed; need a decision or a real environment)
| ID | Finding | Why open |
|---|---|---|
| OPEN-001 | No server-side session revocation; JWTs live 1 year; logout only clears the cookie. | Needs a sessions table / shorter expiry decision. |
| OPEN-002 | OAuth callback `state` is delegated to the provider exchange; no local CSRF/state check. | Needs the provider contract and a real sign-in to test. |
| OPEN-003 | `express.json({limit:"50mb"})` applies to every route including unauthenticated ones. | Needs per-route limits; confirm upload paths first. |
| OPEN-004 | ~~Cron sessions authenticate as a synthetic user with `id = -1` that passes `protectedProcedure`.~~ **Fixed v17 as DEF-016 (offline shim evidence only).** | Cron principals are refused in the tRPC context and on `/api/auth/me` + `/api/auth/session`; a future cron-only endpoint must call `sdk.authenticateRequest` itself. Needs a real cron token to confirm on a live system. |
| OPEN-005 | `defaultPreviewGateway` is an in-memory per-process map (lost on restart, not shared across instances). | Persist or share sessions before multi-instance deploy. |
| OPEN-006 | Preview/runtime version ownership check sees only the newest 50 versions. | Add a direct DB lookup on a real DB. |
| OPEN-007 | Cancelling a run already in `verifying` can leave an assistant message beside a cancelled run. | Needs a product decision. |
| OPEN-008 | Concurrent identical first-time sends with `conversationId = null` can leave one empty conversation. | Rare; fix needs a DB-level dedupe. |
| OPEN-009 | If the process dies after an approval decision is committed but before the run is resumed, a retry returns "already approved" and does not resume (resume is deliberately tied to the call that made the decision). The run stays `waiting_for_approval`. | Needs a resume-recovery sweep; decide expiry policy for waiting runs. |
| OPEN-010 | `applyChangeSet`/`transitionChange` statements in apply-store are keyed by id/status; ownership is enforced earlier inside the apply lock, not by the statement itself. | Re-verify on MySQL; consider joining workspace.userId. |
