 1. Design Objective
  • Every screen follows the same geometry and navigation rules.

  • Equivalent actions appear in equivalent locations.

  • Icons do not shift arbitrarily between screens.

  • Profile/account access uses one global position.

  • Content aligns to one shared grid.

  • Cards, buttons, inputs, dialogs and sheets use shared components.

  • Responsive behavior changes layout deliberately.

  • New AI-generated screens inherit the design system.

 Fixed-position rule: Global header, profile control and primary navigation occupy fixed component slots. Responsive breakpoints may
 change the navigation pattern, but equivalent controls do not randomly move.


 4. Header & Profile Specification
  • Header height: 56 px mobile; 64 px tablet/desktop.

  • Header uses standard left, center and right slots.

  • Profile/avatar is anchored top-right by default.

  • Avatar: 32 px standard; 36 px desktop; minimum touch target 44 × 44 px.

  • Back/title/action structure is identical across detail screens.

  • Header padding follows the global outer gutter.

 11. Cards, Buttons & Forms
  • One primary action per major region.

  • Use shared button variants; no module-specific geometry.

  • Card padding: 16 px mobile; 20–24 px desktop where density permits.

  • Form label above field; 8 px label gap; helper/error below.

  • Validation is not communicated by color alone.

  • Loading preserves component dimensions.

 13. Responsive Behavior
 The Blueprint requires responsive Android/iOS/tablet/desktop/web layouts and light/dark modes. ■filecite■turn10file5■L494-L501■

  • Mobile: single-column content, bottom navigation, full-width primary actions.

  • Tablet: more columns and optional split views for workflows that benefit from simultaneous context.

  • Desktop: persistent left navigation, centered content and multi-column layouts where appropriate.

  • Wide desktop: increase whitespace rather than stretching text/control widths indefinitely.

  • Tables become scrollable or transform into cards on narrow screens.

  • Side panels collapse into sheets on narrow screens.

  • No horizontal overflow or overlapping controls at supported sizes.


 14. Split-View Rules
     Viewport                       Behavior

     Mobile                         Single column; secondary content below or in sheet.

     Tablet                         Optional 60/40 or 50/50 split for approved workflows.

     Desktop                        Primary/secondary split with readable minimum widths.

     Wide desktop                   Keep content within max-width; do not stretch text indefinitely.




 15. Alignment Rules
  • Page titles share one content edge.

  • Cards align to the same grid.

  • Forms share common left/right edges.

  • Primary actions align consistently within their action group.

  • Icon-only controls occupy identical touch-target boxes.

  • Profile placement follows the global header rule.

  • Prefer normal layout systems over arbitrary absolute positioning.

 17. Theme & Accessibility
  • Light and dark modes preserve the same hierarchy.

  • Semantic colors remain consistent across modules.

  • Controls meet accessible contrast requirements.

  • Minimum interactive target is 44 × 44 px.

  • Keyboard focus is visible on desktop/web.

  • Important information is not conveyed by color alone.

  • Text remains usable with increased display/font scaling.

  • Icons and images requiring interpretation have accessible labels.


 18. Navigation & Back Behavior
  • Back returns to the previous meaningful context.

  • Deep links preserve valid route/history state.

  • Tabs preserve selected state where appropriate.

  • Unsaved changes use the shared confirmation pattern.

  • Notifications and AI actions open the exact relevant destination.

 21. Visual Regression
  • Capture approved screenshots at defined viewport sizes.

  • Compare release candidates against approved baselines.

  • Flag icon movement, spacing drift, typography changes, component-size changes and navigation changes.

  • Review intentional changes before updating baselines.

  • Test both light and dark themes.

 23. UI Acceptance Checklist
  • Correct header/navigation template.

  • Profile in defined global position.

  • Correct icon size and touch target.

  • Spacing follows tokens.

  • Typography follows shared scale.

  • Primary/secondary actions are consistent.

  • No overlap at supported viewports.

  • Light/dark themes preserve hierarchy.

  • Loading/empty/error/success states implemented where needed.

  • Keyboard/touch/accessibility checks pass.

  • Visual regression passes.

  • No unapproved component or navigation pattern.

 25. AI Builder Implementation Directive
 Build Geminio OS using this document as the global UI/UX authority. Before creating or modifying a screen, apply the shared design
 tokens, grid, component library, navigation templates, responsive rules and accessibility rules. Do not invent screen-specific positioning
 when an existing system component applies.

 Do not stop at screen generation. Continue implementation, visual validation, responsive testing, regression testing and correction until
 all in-scope screens comply with this specification.

 Professional completion means: consistent positioning, equal spacing, fixed icon/profile placement, stable navigation hierarchy, correct
 sizing, responsive behavior, light/dark consistency and no unintended UI drift.

 Geminio OS should feel like one operating environment, not dozens of separately designed applications. Chat, AI Builder,
 Workspace, Media Studio, Marketplace, Wallet, Developer tools and future modules must share the same grid, spacing, component
 geometry, icon language, profile placement, navigation hierarchy, theme system, responsive behavior and interaction states.
